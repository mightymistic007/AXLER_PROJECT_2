IceStream Observability

Viva & Reviewer Guide

1. Executive Summary (60-Second Pitch)

Elevator Pitch: IceStream is a real-time data-quality control plane for streaming checkout telemetry. Every transaction is governed and validated against strict quality contracts before entering the serving table. If the rolling critical error rate exceeds 2%, an automated circuit breaker trips, isolates bad records to a Dead Letter Queue (DLQ), triggers live WebSocket alerts, and creates an auditable incident. Once clean batches arrive, it automatically recovers. Point-in-time immutable snapshots allow operators to perform time-travel audits.

2. Pipeline Architecture & Data Flow

[Checkout Telemetry] ──> [Stateful Processor] ──> [Quality Assertion Gate] │ ┌──────────────────────────────────────────┴──────────────────────────────────────────┐ ▼ ▼ Clean Events (Critical Errors ≤ 2%) Fault Detected / Breaker Tripped (> 2%) [Iceberg Serving Table & Snapshots] [Quarantined DLQ + Incident Management]

Step-by-Step Flow:

1 Ingress & Stateful Stream Validation

Incoming order events arrive with subtotal, tax, region, currency, and schema version. The engine evaluates each record against 6 governed assertions in memory.

2 Rolling 2% Circuit Breaker Protection

The control plane monitors a sliding 100-event window. If critical quality failures cross 2% (error_rate > 0.02), the circuit trips from closed to open.

3 Dual-Route Isolation (Serving vs. DLQ)

Clean records commit to the lakehouse storage sink. Quarantined records route to SQLite Dead-Letter Storage with exact failure reasons—bad data never infects downstream analytics.

4 Automatic 5-Batch Hysteresis Recovery

To avoid flapping, recovery requires 5 consecutive clean probe batches. Once verified, the circuit closes automatically, or an operator can trigger a manual reset.

5 Lakehouse Snapshots & Time-Travel

Every 24 accepted events commit an immutable snapshot watermark. Operators can inspect point-in-time historical tables to audit historical state.

5. High-Scoring Viva Q&A Cheat Sheet

Q1: Why pre-ingestion quality gates instead of post-write batch validation?
Post-write validation lets corrupted records pollute analytics dashboards and downstream machine learning models before alerts trigger. IceStream acts as an in-line gate, stopping unsafe writes before commitment.
Q2: Why use a rolling window instead of a cumulative lifetime average?
A lifetime average dilutes recent degradation (e.g., 50 failures out of 100,000 events is only 0.05%). A rolling 100-event window detects sudden spikes instantly and clears once the stream stabilizes.
Q3: What is the difference between Quarantine (DLQ) and deleting records?
Deleting bad data loses forensic auditability and financial reconciliation evidence. A Dead Letter Queue preserves the exact malformed payload and rule failure metadata for replay.
Q4: How does this prototype map to production cloud infrastructure?
In production, the generator maps to Apache Kafka / Redpanda, the stateful processor maps to Apache Flink (with side-outputs for DLQ), and the local SQLite storage maps to Apache Iceberg tables on AWS S3 / MinIO.
